# 無料・安全重視の開発基盤

## 現在の状態と費用の境界

この変更は第3段階 `feat/smart-review`（e30af81）を土台にした別PRです。第3段階の82テストを維持します。mainへのpush・マージ、Pages公開、課金設定の変更は行いません。

既存CIはPython/Playwrightのテスト実行でした。リポジトリ内にPagesの公開ワークフロー、CNAME、公開用の有料サービス設定はありません。GitHub APIへの接続が拒否されたため、GitHub側のPages設定、mainの保護設定、外部アプリの自動マージ設定は**未確認**です。設定がないと断定するものではありません。

この基盤のジョブは、対象リポジトリ名、`private: false`、`visibility: public` が確認できる場合に限り、標準GitHub-hosted Linux `ubuntu-24.04` で実行します。GitHubの公開リポジトリ向け標準ランナーの無料利用を前提にし、非公開・状態不明の場合は実行しません。将来リポジトリを非公開にする場合や料金条件が変わった場合は、ワークフローを停止したまま見直してください。

- OpenAI APIキー、従量課金の生成AI API、外部有料サービスは不要です。
- 大容量・有料ランナー、マトリクス増殖、定期実行、成果物アップロード、ビルドキャッシュ保存は追加しません。
- PR更新時、main更新時、明示的な手動操作、公開完了イベントだけを対象とします。並行実行は古い実行を取り消し、15分／10分の上限を設けます。
- 公式アクションは確認した完全なコミットSHAで固定します。パッケージはテスト専用のPlaywrightとPyYAMLです。アプリに依存を追加しません。
- Pages検証だけがGitHub提供の一時的な読み取り用 `GITHUB_TOKEN` で無料のGitHub REST APIを使います。PAT、OpenAIキー、新しい秘密情報の入力は要求しません。API制限・認証失敗時は停止し、別の課金サービスへ切り替えません。

参考となる公式案内:

- https://docs.github.com/en/billing/concepts/product-billing/github-actions
- https://docs.github.com/en/actions/how-tos/manage-workflow-runs/notifications
- https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches

ChatGPT Plusから毎日自動的にCodexの実装を開始する、無料で正式に使える無人実行経路はこの作業では確認できていません。したがって日次の改善案生成、Codex呼び出し、ChatGPT画面の自動操作、セッションCookieの取得、使用量上限を超えた有料フォールバックは実装しません。人が改善案を選び、利用可能なPlus/Codexの範囲で手動開始します。

## 品質ゲート

```sh
python -m pip install -r requirements-test.txt
python -m playwright install chromium
python scripts/quality_gate.py
```

GitHub上のチェック名は **Quality gate** です。

1. `quality/baseline.json` に記録した、全5版の問題データ部分のSHA-256を照合します。現行740問＋ボス4問は既存ブラウザーテストでも確認します。
2. 第2段階の正誤判定ルールをコード部分のバイト単位で照合します。
3. 全版の保存キー・形式番号を照合します。現行 `rikaTangoV2` / schemaVersion 92 を維持します。
4. 登録された既存82テストのIDを検出し、実際に全件実行したことを確認します。
5. 新しいテストもすべて実行します。失敗・スキップ・expected failure・想定外成功・必須テストの未実行は成功と認めません。

ベースラインの更新、テストの削除・無効化、ゲートそのものの変更は人の確認対象です。ベースラインを書き換えて緑にする操作を自動化しません。採点・保存・復習の改良が必要なときは、互換性テストと実際の差分を人が確認する別PRで扱います。

このゲートは、PR作成者がワークフローや検査コードを改変することまで単独で防ぐ仕組みではありません。GitHub側のブランチ保護と人による差分確認が必要です。未確認の保護設定を有効と見なして自動マージはしません。

## 変更ファイル検査と自動マージ

```sh
python scripts/automation_policy.py --base 完全なbaseコミットSHA --head 完全なheadコミットSHA
```

PRではGitHubのbase/headから渡した完全な40桁SHAを使い、NUL区切りのGit差分と実際のファイルモードを検査します。改名は追加と削除として扱います。未知のSHA、読み取り失敗、不完全な差分では停止します。

**低リスク候補の許可リストは `docs/maintenance/editorial-notes.txt` の1ファイルのみ**です。次をすべて満たす必要があります。

- 既存ファイルの変更のみ。追加・削除・コピー・改名は対象外。
- モード100644の通常ファイル。実行可能、シンボリックリンク、サブモジュールは対象外。
- UTF-8、8KiB以下、制御文字・HTML・リンク・コマンド用マークアップなし。
- 別のファイル変更が1件でも含まれたら候補から外す。

このメモは表示・実行・設定・Codexへの指示に使いません。READMEや任意のdocsディレクトリを包括的に許可することもしません。

JavaScript、HTML、問題データ、採点、復習、保存、テスト、権限、依存、ベースライン、ワークフローはすべて許可外で、人による確認が必要です。今回のPR自体も人の確認対象です。

**今回は低リスク候補も自動マージしません。** 出力は常に `auto_merge_authorized: false` / `merge_state: STOPPED` です。マージAPI、`gh pr merge`、リポジトリやPRへの書き込み権限は追加しません。「候補」という分類は承認ではなく、ファイル分類チェックの成功もマージ許可ではありません。

将来自動マージを検討する場合でも、別途人がレビューする設計変更が必要です。少なくとも、公開・無料条件、対象のbase/head SHA、厳格な許可リスト、改変されていない信頼できる検査、必須チェックの**実行成功**、保護設定、承認条件をAPIで確認できることを必須とします。skipped / neutral / pending / unknown を成功に読み替えず、確認できないものが1つでもあれば停止します。

## GitHub側で人が確認する設定

この作業から設定を変更していません。所有者が次を確認するまでは、設定完了・自動リリース可能とは扱いません。

1. Settings → BranchesまたはRules → Rulesetsでmainを保護し、直接push・強制push・削除の制限を確認する。
2. PRとレビューを必須にし、利用できる信頼されたレビュー担当者を指定する。PR作成者自身では承認できない条件も確認する。レビュー担当者がいなければ、自動マージを有効にしない。
3. **Quality gate** の成功と最新baseに対する検査を必須にし、既存の必須チェックが新しい名称と食い違っていないか確認する。
4. Settings → Generalの自動マージ、インストール済みのマージ用アプリ等を確認し、この基盤以外からも勝手にマージされないようにする。
5. 権限・ワークフロー・テスト・ベースラインを含め、人の承認対象の差分を必ず確認する。チェックが緑でも承認済みとは限らない。

## Pages公開後の基本動作確認

公開処理は追加せず、既存の公開が成功した後にだけ **Pages readiness** を実行するワークフローを追加しました。`page_build`、成功した `github-pages` の `deployment_status`、または手動実行を入口にします。定期的にアクセスし続ける処理はありません。

事前確認で以下が分からなければブラウザー確認へ進みません。

- 対象が公開リポジトリである。
- Pagesがbuiltで、ソースがmainのルートである。
- URLが正規の `https://k-yuhi-commits.github.io/rika-tan/` であり、独自ドメイン・リダイレクトがない。
- 公開済みコミットが現在のmainと一致する。旧式Pagesは最新ビルドも照合する。workflow方式はGitHubのボットによる成功イベントを確認する。
- 実際にHTTPS取得したHTMLが、該当コミットの `index.html` とバイト単位で一致する。

確認したHTMLだけを新規ブラウザーで動かし、タイトル、740＋4問、入力モード、回答結果、再読み込み後の1回答の保持、JavaScriptエラーの有無を検査します。ブラウザーからの外部通信は遮断し、個人のプロファイルや学習履歴は使いません。トークンは事前確認ステップだけに渡し、ブラウザーステップには渡しません。

GitHub側のPages設定はAPI制限で未確認です。この作業では公開URLへの実地確認や公開を行っておらず、合成API応答とローカルの同一HTMLで検査処理を検証しました。独自ドメイン、別ブランチ、docsディレクトリからの公開、変換済みHTMLなどは自動で許容しません。適合しない場合は人が設定と仕様を見直す別PRが必要です。

Pages readinessは公開後の検査なので、失敗しても**すでに公開されたページを取り消すことはできません**。公開前の品質ゲートをmainの必須条件にすること、必要な承認と公開設定は別途確認してください。

## 通知・停止・復旧

- GitHubの通知設定でActions失敗通知を有効にし、リポジトリのWatch／Actions画面を確認します。設定が無効ならメール到着は保証できません。外部通知サービスや新しいIssueを自動生成する処理は使いません。
- Quality gate失敗時はマージ・公開へ進まず、ログの最初の失敗を確認します。スキップして緑にする、チェックを外す、ベースラインを機械的に更新することは禁止です。
- Pages readiness失敗時は、その公開が正常と確認できていない状態です。次の変更・マージ・公開を停止し、公開設定、対象SHA、公開HTML、アプリのエラーを確認します。自動で再公開・課金サービスへの切り替え・無制限リトライはしません。
- 誤公開が判明したら、所有者が必要に応じて既存の公開処理を手動停止し、最後に正常確認した版へ戻すための**新しい作業ブランチとrevert用PR**を作ります。mainへの直接pushや強制pushは行いません。
- 復旧先の保存形式との互換性を確認し、既存の学習データを初期化しません。履歴保護修正より前の旧版へ無条件に戻すこともしません。必要なら利用者が学習データを書き出せる状態を優先します。
- 修正PRで品質ゲートを再実行し、人が承認した後に公開操作を判断します。公開後チェックも再度実行します。

## 手動のまま残す工程

改善案の選定、Codexの開始、許可外変更のレビュー、GitHub側の保護・公開・通知設定、マージ判断、公開・復旧操作は人が担当します。追加料金のかかる無人実装や、本番公開を自動的に進める経路はありません。
